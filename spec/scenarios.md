# MVP 场景与验收

状态：Implemented（MVP 验收场景）。以下场景验证 [核心机制](overview.md) 与 [API](api.md)，接口测试位于 `tests/`，真实进程与容器测试入口为 `scripts/smoke.py`。

## 一次正常整理

当前制品和摘要已处理到原始 ID 100。Hymio 陆续写入 101～150，开始整理得到截止 ID 150；Agent 读取这批记录和相关历史，修改草稿制品、记录处理结论、重新生成摘要，然后提交。

验收：提交前普通读取始终看到旧制品和摘要；提交后同时看到新制品、新摘要和游标 150。所有普通制品能按根 ID 与具体原始行双向追溯。

## 新内容还没整理

导入网页或消息，原始读取立即返回完整内容，注入 buffer 返回 ID 和截断预览。普通制品仍是上一版。Agent 可继续按 ID 读原文，不能声称已有对应制品。

## 同一内容被修改

追加同根 ID 的新 context，旧内容在生效制品中的解释暂不改变。dreaming 找出该根关联制品，读新旧原文后修订，提交时更新原始状态和制品。多渠道碰巧同名的内容不会因此共用根 ID。

## 用户自然语言要求删除

追加“删除关于某次错误计划的记录”command。接收成功表示待整理；在 Agent 找到具体目标并提交前，旧制品仍然生效，buffer 显示该请求。

Agent 确定根 ID 后，完整分页查出关联制品，删除或改写它们，修复摘要，再提交根删除状态。提交检查阻止遗漏来源关联。原始日志保留，默认检索不再返回已删除内容，显式历史查询仍可追溯。

## 请求含糊或无需修改

Agent 无法确定“那个东西”指向谁时，记录待澄清和原因；已不存在的目标可记为无需操作。审阅结论允许本批提交，但待澄清不能显示已执行，后续仍可按状态查询；用户补充说明作为新 command 引用旧请求。

## Dreaming 期间继续输入

截止位置固定为 150 后再写入 151、152，包括对本批内容的更新或删除要求。这些记录仍进入 buffer，不能混入当前草稿的输入。提交只消化到 150，151 以后仍然可见且待整理。

## Buffer 满了、来源时间很早或内容很大

超过条数/总大小上限时淘汰最早预览，单条大内容截断。今天导入去年的资料按今天的写入顺序进入 buffer。被淘汰内容保留在原始表，未展示数量可见；dreaming 的完整输入分页仍覆盖它。

## 写入、工具与提交重试

原始写入成功但回包丢失，重用幂等键得到同一行。工具修改成功但回包丢失，不会再次创建制品。同一键不同请求返回冲突。提交成功后断线，恢复查询得到已提交，重复提交不再次移动游标。

## 进程重启或主动放弃

重启后能够读取未结束草稿、截止范围和已保存修改，继续整理。放弃后旧制品、摘要、原始状态和游标均不改变；下次重新处理同一待整理范围。

## 发布与注入同时发生

并发调用注入接口和提交，响应只能是旧摘要配旧游标的 buffer，或新摘要配新游标的 buffer。不得丢掉尚未整理的记录，也不得把新摘要配上已经处理过的重复预览。

## 用户问“之前给你的那个 xxx 后来怎样了”

主 Agent 先看摘要索引和 buffer，通过文本、topic、来源或时间查询候选制品/原文，再按根 ID 读历次变化。结果区分已生效制品与尚未整理的修改/删除请求；线索不足就利用候选继续定位。

## 检索索引延迟

最新原文按 ID 可读；按根 ID 列历史、按引用根 ID 列制品仍然完整。文本/语义搜索报告索引范围。已删除的旧索引命中会被当前权威状态过滤。草稿新制品也能查询到，不必等待索引后台更新。

## 来源乱序、重复同步和迟提交

重复来源版本不重复创建记录。来源版本冲突返回错误，由 Hymio 根据来源版本和本地策略处理，不盲目覆盖。一个较小的本用户 ID 不能在已固定截止之后才提交并被跳过；实现需验证追加与边界截取的顺序保障。

已发布删除的根在同步再次出现时不会自动恢复生效，Agent 需要明确 restore 意图。buffer 里的新材料仍是待审阅内容。

## 一次错误整理与回退

发布后发现提炼有误，回退最近发布。制品、摘要、原始处理/生效状态和游标恢复到前一次，原始日志保持完整，恢复游标之后的输入重新待整理；同一 command 不能在 buffer 显示待整理、在原始读取却显示已执行。重复回退请求只执行一次；活跃草稿必须先结束。

## 用户隔离和来源引用

两个用户的相同外部 ID 不冲突。原始读取、草稿、资源、搜索、来源反查都不能跨用户；提交其他用户的来源引用被拒绝。有效授权由服务验证，不能由 context JSON 或 skill 文字授予。

## MVP 完成条件

通过同一套 HTTP API，在 Docker 服务中完成接收原始内容、开始/恢复整理、制品增删改查、双向溯源、摘要生成、原子发布、注入与回退。重启不丢已确认的数据，协议不泄漏底层数据库或索引结构。无需先实现复杂 topic 层级、语义索引或自动整理策略。
